# INCIDENT INVESTIGATION REPORT: RCA-2025-00114
**Service:** Payment API  
**Completion Date:** 2025-12-05T14:00:00Z  
**Linked Incidents:** INC-2025-00401  
**Investigation Owner:** Payments Platform Engineering  
**Root Cause Category:** Software Defect  
**Business Impact:** EUR 41,200 (estimated)  

## Summary
Intermittent HTTP 500 errors and latency above 5 seconds were observed across card checkout flows after a release of the Payment API.

## Timeline
- 13:40 UTC: Release deployment completed on Payment API pods.
- 15:02 UTC: First connection timeouts on two pods.
- 15:06 UTC: Payment error rates rose above the operational threshold.
- 15:41 UTC: Mitigated by a rolling restart of the pods and a larger maximum pool size.

## Root Cause
Database connection pool exhaustion caused by unclosed SQL sessions inside the payment retry handler block during error response flows.

## Five Whys
1. Why did checkouts fail? Requests timed out waiting for a database connection.
2. Why were no connections free? Connections were not returned to the pool.
3. Why were they not returned? The retry handler did not close the SQL session when the acquirer returned an error.
4. Why was that not found in testing? Tests did not cover transient acquirer errors.
5. Why no alert before customers noticed? Connection leak detection was disabled.

## Contributing Factors
- **Change / Release:** Release changed the retry handler.
- **Process:** No integration test for transient acquirer errors.
- **Monitoring:** Connection leak detection disabled.

## Corrective Actions
Implemented explicit try-with-resources blocks across all repository query methods and enabled HikariCP connection leak detection thresholds.

## Preventive Actions
Add an integration test for the retry path with acquirer errors; alert on pool usage above 90%.
