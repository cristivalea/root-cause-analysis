# INCIDENT INVESTIGATION REPORT: RCA-2024-00299
**Service:** Payment API  
**Completion Date:** 2024-09-30T21:00:00Z  
**Linked Incidents:** INC-2024-00782, INC-2024-01114  
**Investigation Owner:** Payments Platform Engineering  
**Root Cause Category:** Software Defect  
**Business Impact:** EUR 18,000 (estimated)  

## Summary
A mobile app retry sent payment requests again without the idempotency key, so the Payment API processed them twice.

## Timeline
- 17:42 UTC: Incident raised.
- 17:48 UTC: Assigned to Payments Platform Engineering.
- 18:01 UTC: Reassigned to Platform Operations.
- 18:16 UTC: Workaround applied.
- 18:27 UTC: Service restored.

## Root Cause
The mobile app network layer retried timed-out payment requests but built a new request object without the idempotency header. The Payment API accepted the retry as a new payment.

## Five Whys
1. Why were customers charged twice? The Payment API captured the same order twice.
2. Why did it capture twice? The second request had no idempotency key, so it looked new.
3. Why was the key missing? The app retry logic rebuilt the request without the header.
4. Why was that not caught? Integration tests did not cover retries after a timeout.

## Contributing Factors
- **Change / Release:** Mobile app release changed the network retry layer.
- **Configuration:** The API accepted payments without an idempotency key.
- **Process:** No contract test between the mobile app and the Payment API.

## Corrective Actions
Made the idempotency key mandatory on payment requests and refunded duplicates.

## Preventive Actions
Added a contract test for retries between the mobile app and the Payment API.
